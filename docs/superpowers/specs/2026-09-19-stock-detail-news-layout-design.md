# 个股页事件区布局设计（N5b 形态决策）

> 日期：2026-09-19 · 状态：已定稿（用户已确认形态）
> 上游：`2026-09-05-news-module-design.md`（§8 展示与触达）、`../plans/2026-09-14-news-module.md`（N5b）
> 本文档**修订 N5b 的两处落点**，并补齐原设计里没写的布局细节。

## 1. 起因

用户提出的原始诉求：*"我们点进去一个股票，中间显示的是各种数据，旁边最好要跟上最近的重要新闻或相关的内容。"*

这句话里有一个需要当场纠正的前提，以及一个需要保留的直觉。

## 2. 决策依据（全部为代码 / 真实网络实测，不是判断）

| 事实 | 出处 | 后果 |
|---|---|---|
| PWA manifest 锁死 `orientation: 'portrait'` | `frontend/vite.config.js:20` | 主场景是竖屏手机（375–430px），"旁边"没有物理位置 |
| 个股页**一个视口断点都没有** | `KLineChart.vue` 样式块（738 行）无 `@media` | 全站只有 `Dashboard.vue:719` 一处断点。做侧栏等于引入第一套响应式骨架 |
| 图表高度写死 `560px` | `KLineChart.vue:699` | 667px 高的手机上，图 + 工具栏吃掉一整屏 |
| 图表副标题只有"当前价 / 更新时间" | `KLineChart.vue:374` | 页面**已有**一个天然可以承载归因的位置，不必新增卡片 |
| `/api/*` 被 Workbox 缓存 5 分钟 | `frontend/vite.config.js:29-38` | 新闻是时效内容，离线时会用旧响应冒充新响应 |
| `stock_news_em` 每日仅 10 条 | 2026-09-19 实测（与 plan §0.2 一致） | "最近 30 天"必须靠 N3 落库累积，不能靠实时接口 |
| 东财公告**只有标题、没有正文** | 2026-09-19 实测（列名 `代码/名称/公告标题/公告类型/公告日期/网址`） | 公告是信任度最高的信源，却是唯一无法解读的；已补正文抓取（见 §6） |
| 个股新闻是**关键词匹配** | 2026-09-19 真实链路：前 5 条里 3 条是"深沪北百元股数量达217只"这类**提及**该股的行情综述 | 列表必须做相关度过滤，否则事件区会变成噪音区 |

## 3. 形态决策：不做"新闻侧栏"，做"事件与价格同轴"

**否决"数据区 + 新闻侧栏"的三个理由：**

1. **它把解读工作还给了用户。** 一列新闻要求用户自己完成"这条新闻和这条走势有什么关系"的推理——而这正是 spec §1.1 定义的散户三层差里的"解读差"，也是本模块存在的全部理由。做成侧栏等于退化成"更小的东财资讯流"。
2. **过去的事件大多已被价格消化。** plan §0.5 的 `reflected` 判定（事件日期 vs 当日/次日涨跌）本身就承认了这点。把已反映的事件堆在侧栏，信息增量很低。
3. **它踩自己的反目标。** spec §1.2 明确"不做瀑布流信息流"。侧栏 + 无限滚动就是这个东西。

**采用的形态：**

- **归因行进图表副标题**（不新增卡片、不占垂直空间）
- **事件锚定在 K 线上**（`markLine`），与下方事件流**双向联动**
- **桌面端 ≥1024px 才补右侧栏**，且右侧栏优先展示"待发生"

## 4. 布局（三档断点）

| 断点 | 布局 | 内容顺序 |
|---|---|---|
| `< 768px`（手机，主场景） | 单列 | header → **图（副标题 = 归因行）** → **紧凑事件条（默认 3 条 + 展开全部）** → 指标面板 → 完整时间轴（折叠） |
| `768–1023px` | 单列，图表全宽 | 同上，事件区改两列排布 |
| `≥ 1024px` | `grid-template-columns: minmax(0,1fr) 360px` | 左：图 + 指标；右：`sticky` 事件栏，以"待发生"开头 |

**为什么事件条在图**下方**而不是最底部**（修订 N5b-2）：原计划把时间轴插在 `.price-info` 之后，那是页面**最底部**。手机上用户要先滚过 560px 的图 + 指标面板才看得到事件——"最近有什么消息"这个第一眼问题被排到了第二屏。而 `.price-info` 本身与图表副标题信息重复（都是名称 + 当前价），应合并进副标题而非保留一个独立卡片。

**为什么归因进副标题而不是独立卡片**（修订 N5b-1）：原计划在 `.chart-container` **之前**插一张归因卡。那会把图推到第二屏，而图是这个页面的主体。归因是"对这张图的注解"，天然属于图的抬头。

归一后的副标题：

```
当前价 ¥1680.50  +2.31%   ·   相关事件 3 条（公告 2 / 媒体 1）   ·   与事件方向一致
```

**为什么归因不塞进 ECharts 的 subtext**（实现时对 §4 的细化）：设计意图是"归因跟着图、不新增卡片"。但 ECharts 的 `title.subtext` **不会自动折行**，把"相关事件 N 条 + 一句话归因"整句塞进去会把图挤变形。所以拆成两处：

- **图表副标题 = 纯读数**：`当前价: ¥1680.50 | 涨跌: +2.31% | 更新: 10:23:45`
- **紧邻图表下方的事件区标题 = 归因**：`事件与解读` + `近 30 天 3 条（公告 2 / 媒体 1 / 研报 0）` + 归因句

新增的垂直空间只有一行小节标题的位置，而换来了可折行、可选中的真实文本（ECharts 画在 canvas 上，图里的字不能被选中/复制/被读屏软件读到）。

配套删掉了 `stockInfo` 的 `.price-info` 卡片：它与副标题信息重复（都是名称 + 当前价 + 更新时间），实现时把它唯一独有的"行情源更新时间"并进副标题，那张卡片整块删除。

**为什么风险/机会不用"红=风险、绿=机会"**：施工图 §N4 沿用了新浪喜娜的配色（红标风险、绿标机会），但那是**西式**惯例。本应用里 红=`--color-gain`（涨/利好）、绿=`--color-loss`（跌/利空）已有确定含义，再叠一层"红=风险"会让同一个颜色承载两个互相冲突的语义 —— 这正是本文件 §3 与 `KLineChart.vue` 里反复防的那类问题。实现为：**文字标签区分两组**（"机会" / "风险"），机会用涨色、风险用警示色（橙），颜色只作强化。

## 5. 图例与"图 ↔ 列表"的颜色对应（2026-09-19 用户反馈后新增）

用户的反馈：*"折线图上我看到你画了时间戳上对应新闻的具体节点，但是这样去看很麻烦，
你可以用图例去说明这个是一个新闻发生，同时区分事件的方式你可以使用不同颜色的线，
像是一根蓝线是对应新闻列中以蓝色为底色的一个新闻。"*

**采纳其意图，但把颜色这一层从"方向"改成"身份"，方向改用线型承载：**

| 通道 | 改前 | 改后 |
|---|---|---|
| 竖线颜色 | 方向（红=利好 / 绿=利空 / 灰=未判） | **身份**（是哪一条新闻） |
| 线型 | 固定实线 | **方向**（实线=利好 / 虚线=利空 / 点线=未判） |
| 竖线标签 | 固定文字"事件" | **不写文字**（见下方"第二版"） |
| 列表条目 | 只有方向徽章有颜色 | **左侧色条**用事件色，方向徽章不变 |
| 图例 | 只有 ECharts 的 series 图例 | 图表正下方一行 **DOM 图例**：竖线含义 + 线型含义 + 怎么查是哪条 |
| 识别某条 | 无 | **悬停竖线 → 图表下方说明条直接写标题/来源/时间/方向**；悬停列表条目 → 图上那条线加粗 |

**为什么必须做这个交换**：红=利好、绿=利空在本应用已有确定含义，再让颜色承担
"这是第几条新闻"就是同一通道两层语义 —— 文件 §3 与 `KLineChart.vue` 里反复在防这件事。
把颜色让给身份之后，方向信息如果不搬走就会丢，所以搬到了线型上。

**第二版（用户看完第一版后的反馈："你这个线上为什么还有数字，看不懂"）**：
第一版给竖线加了"列表序号"标签，本意是让映射无歧义，但**它要求用户滚到列表里数到第 5 条
才知道那是什么 —— 等于把"这是哪条新闻"换成了另一道题**；而且图上只标最重要的 12 条，
编号不连续（1,2,3,5,7…），看起来更像随便的数值。所以：

- **竖线不带任何文字**，识别改由**悬停直接显示标题**承担（说明条：标题·来源·时间·方向）；
- 颜色只作粗定位（5 色循环，同色靠悬停区分）；
- 列表条目悬停 → 图上那条线加粗（方向反过来也成立）。

**修掉的一个隐藏不一致**：第一版里卡片颜色按"列表序号"取，而竖线颜色按"该日期分组里
影响最高的那条"取 —— 两者可能不是同一条，于是"蓝线点进去高亮的是另一条"。
现在两者同源：`markGroups` 为每个日期给出一个**代表事件**（该日期里列表序号最小的那条），
竖线的颜色、悬停显示的标题、点击跳转的目标全部用它。

**为什么颜色之外还需要交互而不是编号**：色板只有 5 色而事件最多标 12 条，同色必然重复；
编号能解决唯一性但认知成本高（见上）。悬停把"唯一性"交给了交互，不需要用户记住任何东西。

**色板**：`--color-event-1..5`（蓝 `#003eb3` / 青 `#006d75` / 棕 `#873800` /
紫 `#531dab` / 洋红 `#9e1068`）。三条硬约束：
① **全部 ≥4.5:1**（对白 8.97/6.10/8.09/9.85/7.70）—— 门槛比 `--color-chart-*`
那组（只要求图形 3:1）更高；② **不含红、不含绿**，避免与涨跌语义撞义；
③ 与 `--color-chart-*`（数据系列）**分组独立**，不互相借用。

**图例为什么放在 DOM 而不是 ECharts 的 legend**：`markLine` 不是 series，
进不了 ECharts 图例（硬塞一个空 series 会得到一个点了没反应、还会误导人的图例项）；
而且 canvas 里的字读屏软件读不到，而"这条线是什么"恰恰是必须被读到的信息。
位置紧贴图表下方（不是放进右侧事件栏）—— 看图的当场就该能读到它。

**悬停命中为什么不用 ECharts 的 markLine 事件**：`chart.on('mouseover', … componentType === 'markLine')`
依赖"ECharts 是否给 markLine 元素派发交互事件"这个**在本环境无法验证**的前提，
而万一不派发，表现是"鼠标移上去没反应"——静默失效，恰恰是用户要解决的问题。
所以改成容器上的原生鼠标事件 + `chart.convertToPixel` 自己做命中判定，
基准就是画标记用的同一份 `markGroups`，从构造上不可能与图上的线不一致。

## 6. 内容优先级（比布局更重要）

按对决策的价值排序，**不按时间排序**：

| 优先级 | 内容 | 理由 |
|---|---|---|
| 1 | **归因**（今日涨跌 ↔ 事件对照） | 回答用户真正的那个问题："它为什么动" |
| 2 | **待发生**：解禁日、财报预约披露日、股东大会、除权除息 | 唯一真正 actionable 的部分。**候选，须先实测接口**（见 §7） |
| 3 | **已发生的高影响事件**（`impact_level=high`） | 按影响强度排，不按时间 |
| 4 | 常规事件流 | 默认折叠，点击展开 |

配套硬约束：

- **信源权重必须视觉分层**，不能混成一个流。信任度是 公告 1.0 / 研报 0.8 / 媒体 0.7 / 舆情 0.4（plan §0.5）。⚠️ 注意它与 `source_level` 的数字顺序**不一致**（研报级别 3 > 媒体 2，但信任度也更高），不要写成 `1/level`。
- **每条必须带 `plain_summary`**（"发生了什么 + 对持有者意味着什么"）。只有标题的时间轴 = 这个模块白做。
- **`direction` 为 `null` 时显示"信息不足，不判断方向"**（spec §6 硬约束），**不要**用灰色"中性"糊过去——"不判"和"判了中性"是两件事。
- **空态要有结论**："近 30 天无重大事件，近期波动大概率跟板块/大盘走" + 一条板块对照。**"没有新闻"本身就是结论**，不能显示"暂无数据"。
- **列表要有上限**：默认 3 条。

## 7. 事件锚定 K 线的实现要点（三个必须先想清楚的坑）

1. **公告会落在非交易日**（周末/节假日），而 xAxis 是交易日 category —— 值不在轴上 `markLine` 就不渲染。需要把事件日期映射到窗口内**最近的交易日**。
2. **盘后公告影响的是次日价格**，不是当日。锚点应取**次一交易日**，不是公告日期。
3. 事件必须在 `range` 切片**之后**过滤（`KLineChart.vue:202`），否则标记会落在可视窗口外。

另需注意：`published_at` 对公告是**纯日期**（`00:00:00`），同一天的公告之间没有可靠先后顺序，不要把它当因果序（见 `news_client.parse_datetime` 的 docstring）。

## 8. 开放项（未验证，不得直接写进实现）

- **"待发生"数据源**：2026-09-19 实测 `ak.stock_gddh_em()`（股东大会）**可用**，1954 条，含 `召开开始日 / 股权登记日 / 提案`；但 `stock_restricted_release_queue_em`（解禁）返回空、`stock_report_disclosure`（预约披露）JSONDecodeError、`stock_fhps_em`（分红）TypeError。**在补齐实测之前，"待发生"只做股东大会一项**，其余不实现。
- **个股新闻相关度过滤**：**已实现**（2026-09-19，`news_client.is_about_the_stock`）。
  实测依据：`stock_news_em` 是关键词匹配，600519 的 10 条里混着「深沪北百元股数量达217只」
  「主力动向：9月16日特大单净流入367.77亿元」这类大盘综述。规则是**只看标题**里有没有
  股票名（名字拿不到时看标题里有没有代码；两者都没有则返回"无从判断"，退回关键词闸门，
  而不是判成"无关"）。实测效果：10 条 → 放行 3 条（中报、被执行 ×2），跳过的 7 条含全部大盘综述。
  - 只看标题是**刻意的**：把正文也算进去会被骗过 —— 那些综述的正文里就列着"贵州茅台"和 600519。
  - 代价是漏掉"标题不提公司名、正文才提"的报道（实测「i茅台再调整规则…」）。
    取舍偏精确：判错的代价是花一次模型调用解读一篇大盘综述，不判的代价只是那一行显示"未解读"
    （**它仍然留在时间轴里，不会被删掉**）。
  - 该规则只影响"是否花 LLM 调用"，不影响"是否展示"。
- **是否要把"不相关"的条目从时间轴里也去掉**：仍未定。当前选择是**展示但不解读**——
  隐藏数据的错误比多显示一行的错误更难发现。

## 9. 与实施的关系

- 依赖 N1（取数）+ N2（结构化抽取）+ N3（落库与查询 API）先打通——N5b 本身只是 1–2 天的展示层工作，但它站在 5–8 天的地基上。跳过地基的 N5b 是一个空壳。
- **公告正文抓取已完成**（`news_client.enrich_announcement_bodies`，走实测可用的东财正文 JSON 接口）。个股页调用取数端点时必须传 `withBody: true`，否则公告区全是"信息不足，不判断方向"。

## 10. 验收标准

- 手机（375px）上：进页面第一屏能看到归因行；事件条在图表正下方，不需要滚过指标面板。
- 桌面（≥1024px）：右侧 360px 事件栏 `sticky`，滚动时保持在视口内。
- K 线上的事件标记数量 == 事件流里落在当前可视窗口内的条数。
- 点 K 线标记 → 事件流滚到对应条目并高亮；点事件 → 图上对应日期高亮。
- `/api/v1/news` 走 `NetworkOnly`，新公告不受 5 分钟缓存影响。
- 空数据时显示结论文案，而不是"暂无数据"。
