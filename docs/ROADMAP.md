## 零、为什么是这个顺序（决策依据 · 先读这一节）

### 0.1 一句话诊断

> **这个项目不缺功能，缺的是"让已有功能变成可信资产"的顺序。**
> 策略 Agent 写完了、同花顺写完了、新闻设计好了，但前两者的代码还没锁进版本库、测试是红的、文档在漂移。在这种状态下继续加功能，**每一次新增都在放大而不是缩小不确定性**。

### 0.2 决策 1：为什么第一件事是 N0 地基（提交 + 测试回绿），而不是直接写新闻

| | |
|---|---|
| **理由 A：可归因性** | 接下来要跨 Python/Java/前端加约 15 个文件。如果这 15 个文件叠加在已有的 **101 项未提交改动**之上，任何 bug 都无法判断是"新闻引入的"还是"THS 遗留的"，出问题只能二分回滚整坨。先提交，新闻的 diff 就是独立可审的一层。 |
| **理由 B：测试红的根因是系统性的** | 5 个失败全是 401，根因是 `app.py` 加了 `x-internal-token` 中间件而测试没带头 —— 这是**测试装置缺失**，不是某个用例写错。新闻模块要新写 `tests/test_news_client.py`，若不先修装置，新测试会**一模一样地再踩 5 次**。 |
| **理由 C：成本收益比最高** | 半天工作量，换来"随时可回滚 + 有回归网"。这是整份路线图里性价比最高的一步。 |
| **反过来做会怎样** | 直接写新闻 → 一周后测试仍然红（还多了新闻的红）→ 无法区分"新闻代码错"和"鉴权头没带" → 只能靠手工 curl 逐个验证，返工率大幅上升；同时 101 项改动的丢失风险持续存在。 |

### 0.3 决策 2：为什么主线是新闻（搜索+分析），而不是持仓或 PWA

| 候选主线 | 它改变什么 | 判断 |
|---|---|---|
| **新闻/资讯（搜索 + 分析）** | **改变"产品是什么"** —— 把"能查行情"变成"能看懂行情"，对应散户真正的三层差：时间差、解读差、噪音过滤差 | ✅ **选它** |
| 持仓与成本（Phase 2） | 让"盈亏数字可信"，是**记账**，不改变产品形态 | 排后，但不远（见决策 5） |
| PWA 推送（Phase 4） | 让已有功能**触达**用户，是放大器 | 排后（见决策 6） |

**选新闻的三个硬理由**：

1. **差异化唯一落点**。README 自己写的定位是"不只是查行情，更是看懂行情"。行情查询、K 线、预警、策略回测 —— 这些竞品都有；**"这条公告对持有它的我意味着什么"** 只有这个模块回答。持仓是后台记账，推送是渠道，两者都不改变产品身份。
2. **边际成本最低（复用最大化）**。新闻模块站在**已经建好的**基础设施上：akshare 取数管道（有）、`llm_service`（有）、两级缓存（有）、消息中心 + SSE 触达（有）、Alert 通道（有）。而持仓要新建券商/mniQMT 或 CSV 通道（**从零建**），PWA 推送要新建 VAPID + 订阅表 + Service Worker 改造（**从零建**）。同样投入，新闻的"新地基"最少。
3. **最大风险已被排除**。数据源是这类模块的生死线，而**四个 akshare 接口今天已真实跑通**（公告 469 条/日、新闻 10 条、研报 771 条、财新要闻 100 条），字段名逐个核对完毕。反观另外两个候选：miniQMT 通道取决于你用什么券商（**未定**），Web Push 在 iOS 上有"必须添加到主屏才生效"的硬约束（**体验不可控**）。先做不确定性已被消掉的那条。

### 0.4 决策 3：为什么新闻内部是「搜索先行」，而 spec 把「收盘汇总」放在 P0

| | |
|---|---|
| **理由 A：搜索是最轻的完整闭环** | 取数 → 落库 → 查询 → 展示，四步就是一条能演示的链路。汇总卡要额外叠 Job 调度 + 逐用户幂等 + 触达，是**最重**的一块。先用 2–5 天跑通一条完整链路，比用两周搭一条还没验证过质量的管道更稳。 |
| **理由 B：汇总卡是搜索的特例** | 汇总卡 = `类型=全部, 天数=1, 只看自选`。搜索打通后它几乎是免费查询。**反过来不成立**：先做汇总卡，你还是得先有搜索的取数+落库能力。 |
| **理由 C：质量验证要趁早** | 本模块最大风险是 **LLM 误判利好/利空**（比"没有功能"更糟，会误导决策）。要做人工抽查、要调 prompt，前提是**能看见一批真实数据**。先建重型管道再验质量 = 发现问题时返工面巨大。 |
| **反过来做会怎样** | 先做汇总卡：两周后你有了一个每天定时运转的 Job，但没人知道它抽出来的 `direction` 准不准 —— 因为验证质量的通道（能翻看一批事件）最后才建。 |

### 0.5 决策 4：为什么个股页事件区 / 汇总卡放 N5

它们**在代码上依赖 N3（库）和 N4（查询 + 卡片渲染）**。提前做只能写出一次性代码：等 N3 的字段或 N4 的组件一改，前面写的那版就废了。前端展示永远排在数据契约稳定之后。

### 0.6 决策 5：为什么持仓与成本排在新闻之后、PWA 之前

| | |
|---|---|
| **它是一个正在恶化的地基问题** | `PnlPercentEvaluator`（盈亏百分比预警）读的是 `favorite_stocks.buy_price`。而同花顺同步**刻意不写这个字段**，理由写在 THS 设计文档里：**"加入价 ≠ 成本价"**。于是现在"自选参考价"和"真实买入成本"挤在同一个字段里 —— 这正是人家已经踩过一次的坑。越晚解耦，脏数据越多，盈亏预警越不可信。 |
| **但它是"记账"不是"产品"** | 所以排在新闻之后：先让产品更懂用户，再让数字更准。 |
| **它还解锁两件事** | ① 持仓页（README 已承诺却不存在）；② 策略/模拟盘可以基于**你的真实成本**给盈亏口径，而不是虚拟初始资金。 |

### 0.7 决策 6：为什么 PWA 推送排在更后

| | |
|---|---|
| **它没有产品不确定性** | 骨架（manifest / Service Worker / 图标 / dist）已经在，缺的是 VAPID 密钥、订阅表、`push` 事件、iOS 引导文案 —— 纯工程活，早做晚做工作量一样，不存在"越晚越难"。 |
| **它的价值是放大器，而放大器需要先有信号** | 推送要推的内容来自 Alert 和（后来的）`NewsDigestJob`。**新闻做完，推送才有新内容可推**；否则只是把现有价格预警从站内搬到锁屏，价值有限。 |
| **依赖关系** | Phase 4 依赖 Phase 2 的告警口径 + 新闻模块的汇总结论，天然靠后。 |

### 0.8 决策 7：为什么 Phase 5 是"四选一"而不是排期

模型前向验证、多股组合、实盘通道、合规化 —— 四个方向**互斥且都重**，且都建立在"前面的功能长期真的有用"这一前提上。特别是实盘：spec 明确标为非目标，一旦做就要单独立项 + 风控设计（**会动真钱**）。在没看到前面阶段的真实使用效果前排期，是凭空承诺。

### 0.9 依赖关系与解锁价值

```
        ┌──────────────────────────────────────────────────────────┐
        │ N0 地基：可回滚 + 有回归网                                 │
        └───────────────┬──────────────────────────────────────────┘
                        ▼
   N1 取数 ──► N2 分析 ──► N3 落库+搜索API ──► N4 搜索页+解读弹窗 ★主目标
                        │                              │
                        └──────────► N5 事件时间轴 + 收盘汇总卡 ◄┘
                                            │
                                            ▼
                                   Phase 4 推送（有内容可推）
        ┌───────────────────────────────────────────────────┐
        │ Phase 2 持仓与成本（与新闻正交，独立推进）           │──► 盈亏预警口径变准
        └───────────────────────────────────────────────────┘
```

| 阶段 | 完成后你**多出什么能力** |
|---|---|
| N0 | 改动可回滚、`pytest` 全绿、新代码 diff 独立可审 |
| N1 | 想拿哪只股票的公告/新闻/研报，命令行就能拿（数据自由） |
| N2 | 一条公告进 → 大白话解读 + 风险/机会红绿标注出 |
| N3 | 搜索 API 落库去重，**越用库越全**（补上"个股新闻只有 10 条"的先天不足） |
| N4 | **网页上能搜新闻、能点开看解读** ← 你要的主线闭环达成 |
| N5 | 不用主动搜，收盘后自动看到"与你自选相关的 N 条" |
| Phase 2 | 盈亏数字基于真实成本，预警不再误报 |
| Phase 4 | 手机锁屏直接收到预警，点击直达个股页 |

### 0.10 建议节奏（约 3 周完成主线）

| 时间 | 内容 | 里程碑 |
|---|---|---|
| 第 1 周 | N0（0.5 天）+ N1 + N2 | 命令行能取真实资讯，且公告能出大白话解读 |
| 第 2 周 | N3 + N4 | **主目标达成**：网页能搜、能读解读 |
| 第 3 周 | N5 + 缓冲（补测试、修文档、质量抽查） | 个股页有事件背景，Dashboard 有收盘汇总 |
| 之后 | Phase 2 持仓 → Phase 4 推送 → Phase 5 择一 | |

| 不做 | 原因 |

| MCP 接入外部数据源 | spec 已列为非目标；当前 akshare 四源已够验证产品假设 |

## 九、关键风险与决策点

### 风险

| 风险 | 影响 | 缓解 |
|---|---|---|
| 🔴 **101 项未提交改动** | 一次误操作/一次错误的 `git checkout` 就丢一整个功能 | **Phase 0 第一件事就是提交** |

| 🟡 akshare / 东财接口变更 | 行情、公告拉取失败 | 封装集中 + 巨潮备选 + 手动重试入口 |
| 🟡 LLM 抽取幻觉（误判利好利空） | 误导用户 | `confidence` 门槛 + 置空机制 + "影响方向 ≠ 涨跌预测"文案 |
| 🟢 编码事故复发 | 中文乱码、前端文案错 | `.editorconfig` + 编辑器统一 UTF-8 + Phase 0 清理 |
| 🟢 文档与代码漂移 | 误导后续开发（`WORKFLOW.md` 已经发生过一次） | 每阶段收尾必须同步 README 路线图 |

### 需要你拍板的决策点

1. **未来 1–2 个月主线**：是「个人助手再深挖（Phase 3 新闻事件）」还是「可用性与触达（Phase 4 推送）」？→ 建议 **Phase 0 → 1 → 2 → 3**，因为持仓成本是预警和策略的共同地基。
2. **THS 自选里的指数怎么办**（P1-3）：过滤掉，还是让行情/预警支持指数？
3. **是否有"给他人用"的时间表**：若有，Phase 3 的合规预留（免责、禁止句式、降级开关）必须从第一天就做，否则返工。
4. **是否接券商自动持仓（miniQMT）**：取决于你用的是哪家券商，决定 Phase 2 的通道优先级。
